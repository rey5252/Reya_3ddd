# Текстури Fortress Protocol

Процедурні тайлові текстури для 3D-моделей веж (контракт — `SPEC.md`, розділ «Текстури»).
Нічого не малюється вручну: усе генерується скриптами на Python (numpy + Pillow) і може бути
перезібране однією командою.

## Структура

```
models/
  texkit.py                    ← бібліотека: тайлові шуми, панелі, заклепки, смуги, подряпини,
                                 normal map з карти висот, save_set(), contact_sheet()
  meshkit.py                   ← моделі; Model.save() читає bindings.json і накладає текстури
  build_all.py                 ← перезбирання всього (текстури → прив'язки → моделі)
  textures/
    gen_allied.py  gen_soviet.py  gen_empire.py   ← генератори наборів
    allied/  soviet/  empire/  ← <name>_dif.png, <name>_nrm.png, <name>_spm.png, _sheet.png
    make_bindings.py           ← автоматична прив'язка «матеріал моделі → текстура»
    bindings.json              ← результат make_bindings.py (його читає meshkit)
  glb/                         ← готові моделі, посилаються на ../textures/<set>/...
```

## Як генеруються текстури

`python3 -I models/textures/gen_<set>.py` (шляхи рахуються від `__file__`) будує кожну текстуру
з карти висот (панелі з фасками, шви, заклепки, жолобки), до якої додаються кольори фракції,
запечене світло зверху (`texkit.shade`), бруд у западинах і потертості лише по краях
(`texkit.edge_wear`). Усі шуми й фільтри «загортаються» по краях, тож текстури безшовні.
Розмір — 512×512, щільність на моделі — **1 тайл = 2 м** (2 одиниці моделі).
`_sheet.png` у кожній теці — контактний аркуш для перегляду (dif | nrm | spm | dif 2×2).

Обов'язкові імена (SPEC):

| набір | текстури |
|-------|----------|
| `allied` | `panel_white`, `panel_blue`, `chrome`, `energy_cyan`, `plate_steel`, `dark_metal` |
| `soviet` | `steel_olive`, `paint_red`, `hazard`, `copper_coil`, `concrete`, `sandbag`, `plate_steel`, `dark_metal`, `brass` |
| `empire` | `armor_white`, `lacquer_crimson`, `trim_black`, `energy_teal`, `stone`, `plate_steel` |

## Конвенція файлів `_dif` / `_nrm` / `_spm`

- `<name>_dif.png` — колір (diffuse/albedo), sRGB.
- `<name>_nrm.png` — tangent-space normal map у конвенції **OpenGL (+Y вгору, як у glTF)**.
  RA3 (DirectX) очікує **інвертований зелений канал** (−Y). Інверсію робить
  `scripts/blender_export_w3x.py` під час конвертації (вимикається `--no-flip-normal-g`).
  `<!-- VERIFY: порівняти з ванільними _NRM з арту SDK — якщо рельєф у грі «запалий», прибрати інверсію -->`
- `<name>_spm.png` — маска RA3: **R — блиск (specular), G — самосвітіння, B — маска кольору гравця**
  (house colour). `<!-- VERIFY: розкладку каналів перевірити проти ванільних *_SPM.dds; у деяких
  шейдерах RA3 канали можуть бути іншими -->`. glTF цю маску не використовує (у прев'ю її не видно);
  її підхоплює лише експорт у W3X.

## Прив'язка до моделей: `bindings.json`

Формат: `{ "<TowerId або ім'я моделі>": { "<ім'я матеріалу>": "<set>/<name>" } }`.
Значенням може бути й об'єкт `{"texture": "<set>/<name>", "white": 0.45, "tile": 2.0, "normal_scale": 1.0}`.

Файл генерує `python3 -I models/textures/make_bindings.py` (`--check` — лише показати, не писати):

1. відкриває кожен `models/glb/*.glb` (JSON-чанк), бере імена матеріалів;
2. фракцію визначає за префіксом імені (`Allied` → `allied`, `Soviet` → `soviet`, `Japan` → `empire`);
   наноядра (`<TowerId>Nanocore`) — окремі записи;
3. ручні винятки `MANUAL` мають пріоритет; напівпрозорі матеріали (щити, ореоли) і світні
   (emissive) лишаються без текстури, крім дозволених у `ENERGY_OK` (`energy_cyan` / `energy_teal`
   для широких м'яко світних поверхонь);
4. далі — таблиця ключових слів `KEYWORDS` (regex по імені матеріалу); якщо кандидатів кілька,
   вибирається текстура, середня яскравість якої після тонування найближча до кольору матеріалу;
5. якщо текстура після стандартного тонування вийшла б значно світлішою за задуманий колір
   (темний матеріал на світлій текстурі), записується менший `white` (автоматично).

Геометричні жовто-чорні смуги (`haz_y`/`haz_k`, `hazard_y`/`hazard_k`) навмисно **не** отримують
текстуру `soviet/hazard` (її смуги конфліктували б зі змодельованими): жовті смуги лишаються
пласкою фарбою, чорні — `soviet/dark_metal`. Текстура `hazard` готова для нових поверхонь —
прив'язати її можна через `MANUAL`.

Після зміни матеріалів у генераторі моделі перезапустіть `make_bindings.py` (або `build_all.py`),
інакше нові матеріали лишаться без текстур.

## Що робить `meshkit.Model.save()`

Для кожного прив'язаного матеріалу, чий `_dif.png` існує:

- **UV — box-проєкція** зі світових координат: кожен трикутник проєктується вздовж домінантної осі
  своєї нормалі, 1 тайл = 2 одиниці; вершини розщеплюються лише там, де сусідні трикутники
  проєктуються по різних осях (позиції, нормалі й трикутники не змінюються);
- `baseColorTexture` = `../textures/<set>/<name>_dif.png`, `normalTexture` = `..._nrm.png`
  (зовнішні файли, `uri` відносно `.glb`), семплер `REPEAT` + mipmaps (`LINEAR_MIPMAP_LINEAR`).
  Дотичні (`TANGENT`) не пишуться — three.js і Blender обчислюють їх самі;
- `baseColorFactor` зсувається на 70 % до білого (`TEX_TINT_WHITE`, або `white` із прив'язки):
  видно власні кольори текстури, а відтінок моделі зберігається; emissive не змінюється;
- у `extras` матеріалу: `ft_texture` (яка текстура) і `ft_design_color` (колір до тонування).

Неприв'язані матеріали лишаються без текстур. Якщо файлу текстури немає — попередження в stderr,
матеріал зберігається без неї. Вимкнути текстури: `FT_NO_TEXTURES=1` або `model.save(path, textures=False)`.

## Перезбирання всього

```
python3 -I models/build_all.py              # gen_*.py → моделі → make_bindings.py → моделі з текстурами
python3 -I models/build_all.py --skip-gen   # без перегенерації текстур
python3 -I models/build_all.py --no-textures
```

Наприкінці друкується підсумок: трикутники/вершини на модель, текстуровані матеріали, відсутні
файли текстур. Помилка одного скрипта не зупиняє решту.

Окремо: `python3 -I models/textures/gen_soviet.py`, потім `python3 -I models/textures/make_bindings.py`,
потім `python3 -I models/towers/<TowerId>.py`.

## Як текстури потрапляють у гру

1. **Blender.** `scripts/blender_export_w3x.py` імпортує `.glb` (вбудований glTF-імпортер Blender
   підтягує зовнішні PNG за відносними `uri`, тож тека `models/textures/` має лежати поруч із
   `models/glb/`), конвертує кожну текстуру в `<out_dir>/FT<Set>_<name>_<dif|nrm|spm>.tga`
   (normal map — з інверсією G) і під'єднує їх до параметрів шейдера `DiffuseTexture` / `NormalMap` /
   `SpecMap`. Текстуровані матеріали отримують фракційний шейдер (`ObjectsAllied.fx` тощо,
   `<!-- VERIFY -->`), решта — `DefaultW3D.fx`.
2. **W3X.** Файл моделі (`FTPrismSpire.w3x` …) посилається на текстури **за іменем** асету
   (`FTAllied_panel_white_dif` тощо), а не за шляхом; поруч плагін пише `Texture`-асети (.xml).
3. **Мод.** Текстури кладуться в `FortressTowers/art/` разом із `.w3x`. SDK приймає `.tga`
   (BinaryAssetBuilder сам стискає їх у DDS); за бажання можна заздалегідь конвертувати в `.dds`:
   `_dif` — DXT1 (або DXT5, якщо є альфа), `_nrm` і `_spm` — DXT5 / без стиснення, усі з mipmaps
   (напр. `texconv -f BC1_UNORM -m 0 ...` або `nvcompress`). Розмір 512×512 — степінь двійки, як треба.
   `<!-- VERIFY: формат і стиснення порівняти з ванільними текстурами споруд у SDK -->`
4. Ім'я W3X-контейнера моделі — `FT` + назва без префікса фракції (SPEC, «3D-моделі»).

## Перевірка рендером

Прев'ю з текстурами — three.js (glTF): відкрити `.glb` у будь-якому glTF-переглядачі, що бачить
теку `models/textures/` за відносним шляхом `../textures/` (наприклад, локальний веб-сервер із
кореня `models/`). Канал `_spm` у такому прев'ю не показується.
